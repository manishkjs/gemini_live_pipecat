A voice agent prompt behaves differently from a chatbot prompt. In Gemini Live, your `systemInstruction`, your `tools`, the conversation so far, and any updates you send during the call all end up in one prompt. Each piece has a fixed place in it.

The model reads that whole prompt again on every turn, and you pay for it again on every turn. So the order matters. It tells you what to keep short and where to put instructions that change during a call.

---

## 1. How Gemini Live builds the prompt

On every turn, Gemini Live stacks the prompt in this order, top to bottom:

```text
ROLE_SYSTEM                   (set by Google, you can't change it)
  1. Spoken-dialog rules      Built-in rules for talking out loud
  2. Voice sample             About 224 to 239 audio tokens for the voiceName you picked

ROLE_DEVELOPER                (set by you when the session starts)
  3. Tool definitions         setup.tools (comes first)
  4. Your instructions        setup.systemInstruction (comes after the tools)
----------------------------- reuse line: the server can reuse everything above between turns
ROLE_USER / ROLE_ASSISTANT
  5. Conversation so far      Earlier turns, kept as audio plus transcripts.
                              If the caller cut the agent off, only the audio
                              they heard is kept.
ROLE_CONTEXT
  6. Time and location        Added by the server

ROLE_USER
  7. What the caller just said    The latest caller turn (audio plus transcript)

ROLE_CONTEXT
  8. Session updates          What you send during the call (current step, saved facts)
```

The `ROLE_*` labels describe how the server orders the prompt. You won't see them in the API.

A few terms come up a lot on this page:

- Reuse line: the server keeps its work on the top part of the prompt so it doesn't redo it every turn. The diagram below calls that top part the preamble and the line the prefix cache boundary. This makes replies faster. It doesn't make them cheaper, because those tokens are still billed on every turn.
- Session updates: text you add at the very bottom of the prompt while the call is running. Examples are a step card (the instructions for the current step of the call, also called a phase card) and a short list of facts you've saved about the caller. Some docs call this "tail context".
- `WHEN_IDLE`: a scheduling option on a tool response. The update is delivered after the model finishes speaking, so it doesn't cut the model off.

### What this means for your prompt

#### Your instructions aren't at the very top

`ROLE_SYSTEM` belongs to the server. It holds Google's spoken-dialog rules and the voice sample for your `voiceName`. Your `systemInstruction` goes into `ROLE_DEVELOPER`, right after your tool definitions. Fifteen to twenty large tool schemas can put 2,500 or more tokens in front of your instructions, and you pay for them on every turn. Declare only the tools the call needs, ideally 1 to 5.

#### The bottom of the prompt has the most pull

Your instructions sit at the top. After twenty turns, a lot of audio and transcript sits between them and the caller's latest words. Session updates go at the very bottom, right after what the caller just said, so the model tends to follow them closely in its next reply. Put things that change during the call there: the current step, facts you've confirmed, or what's in the caller's cart.

#### Changing the top block means rebuilding it

Your tools and instructions form the block above the reuse line. If you change either one, the server has to rebuild that block. Adding session updates at the bottom leaves it alone.

#### The server decides what the caller heard

Only the Live server knows the exact moment a caller cut in. When that happens, it drops the unplayed part of the agent's audio from history and ends the partial transcript with `"—"`. That way the model knows the caller never heard the rest of the sentence. The server also handles this when a dropped connection picks up where it left off with `SessionResumptionConfig`: it restores the saved history directly instead of processing the raw audio again.

### Where each piece of information goes

| What it is | Where to put it | How often it changes | Effect |
| :--- | :--- | :--- | :--- |
| Persona, tone, speaking pace, language and grammar rules | `setup.systemInstruction` | Once, at the start (about 300 to 500 tokens) | Part of the reused top block |
| Tool definitions (`functionDeclarations`) | `setup.tools` | Once, at the start | Part of the reused top block. Changing it means a rebuild |
| Rules for the current step, such as "Step 2: verify identity" | Session update: a tool response with `scheduling=WHEN_IDLE`, or a `clientContent` message between turns | When the step changes, about 3 to 5 times per call | Top block stays as it is |
| Confirmed caller facts, such as name, postal code, or ticket ID | Session update, as a short summary under 60 tokens | After you capture a new fact | Top block stays as it is |
| Large catalogs or policy documents (over 1,000 tokens) | Behind a lookup tool that returns a short summary (about 25 tokens) the agent can say out loud | Only when needed | Nothing added to the fixed prompt |

## 2. Keep `systemInstruction` under 500 tokens

You pay for `systemInstruction` again on every turn. A 4,000-token instruction in a 10-turn call adds up to 40,000 billed text tokens, which is `$0.020` to `$0.030` for the instruction alone. Keep yours under 500 tokens and split it into four short blocks:

```text
1. PERSONA AND DELIVERY
You are Maya, a senior technical support specialist at Cymbal Fiber.
Speak in a warm, calm, conversational tone. Keep every reply to 1 or 2 short sentences (15 to 35 words), then pause so the caller can answer.
Read confirmation numbers, postal codes, and phone numbers one digit at a time ("four, two, nine").

2. LANGUAGE AND BACKGROUND NOISE
Speak only in English. Keep every word in English, even if you hear background noise, coughs, or a strong accent.
The caller may be somewhere noisy. Ignore background conversations, side chatter, and sounds not directed at you.

3. TOOL AND TURN RULES
Say the opening greeting first, without calling any tools.
On later turns, when you call a tool, first say a short acknowledgment ("Let me check your line status right now."), then make the tool call and stop talking. After a tool call, your only job is to listen.

4. OPENING STEP (GREETING AND REASON FOR CALLING)
a) Greet the caller briefly and ask how you can help today.
b) Listen to their full answer.
c) Call lookup_customer_account with the issue they described, and wait for the result before moving on.
```

### Why it's written this way

#### Say what to do, not what to avoid

Rules like *"Do NOT narrate tool calls"* or *"Never repeat yourself"* often backfire in live audio, because naming the unwanted action keeps it front of mind for the model. Tell the model what to do next instead:

| Instead of this | Write this |
| :--- | :--- |
| *"Do NOT announce when you are calling a function or read out parameter names."* | *"Before you call a tool, say one natural sentence ('Let me check that for you.'), make the call, and stop talking."* |
| *"Never ask multiple questions in the same turn or give long paragraphs."* | *"Ask one question per turn, keep your reply under 30 words, and wait for the caller to answer."* |
| *"Do not switch languages if you hear background noise."* | *"Speak only in English on every turn, even if background voices or accents sound like another language."* |

#### Stop the agent from calling tools before it says hello

Turn 0 is the moment before the caller has said anything. Without a clear opening rule (*"Say the opening greeting first, without calling any tools"*), the model may call `switch_phase` or a lookup tool on Turn 0, before it greets the caller. That can load a 500-token step card before the caller speaks and roughly double the prompt tokens for Turn 1 (from 488 to 1,023 in one measured session).

#### Spell out each step with a, b, c

When a step involves asking a question and then calling a tool, write the order out as lettered steps. Otherwise the model may call the tool before the caller has answered.

#### Say each instruction once

If a tool response or session update already gives the instructions for a step, take that instruction out of `systemInstruction`. When the same instruction appears at both the top and the bottom of the prompt, the model may say it twice.

## 3. Audio traps to avoid

Native audio models turn your text instructions straight into speech. Some habits from text prompting cause trouble here:

### Don't use square brackets

Avoid tags such as `[PAUSE]`, `[SYSTEM_NOTE]`, or `[EMPATHETIC]`. The model may read them out loud (*"bracket system note bracket"*) or switch to an over-acted voice. Write plain sentences instead, like `"System update for agent: ..."`.

### Don't ask the model to stay silent for a whole turn

If the model produces no audio for a turn, the server also skips the caller's input transcription for that turn. Your transcript log and state machine then miss what the caller said. If you need silence while background work runs, mute the audio on your side, or send the tool response with `FunctionResponseScheduling.SILENT`.

### Don't send `clientContent` while the model is talking

A `clientContent` message with `turn_complete=True` acts as a new user turn and cuts the model off mid-reply. With `turn_complete=False`, the current reply usually finishes (14 of 16 measured runs on Vertex AI `gemini-3.8-live` and `gemini-live-2.5-flash-native-audio`), but the update only takes effect on the next turn. Wait for `turnComplete` first, or put the update in a tool response with `scheduling=WHEN_IDLE`.

## 4. Guiding the call with session updates

To take a call through several steps without growing the top block:

1. Keep `setup.systemInstruction` and `setup.tools` the same for the whole call.
2. Send step changes and saved facts as session updates. Either return them in a tool response with `scheduling=WHEN_IDLE`, or send them with `clientContent` (`turn_complete=False`) right after `turnComplete`.
3. In languages with grammatical gender, such as Hindi, Spanish, or French, add a one-line grammar reminder to every step card. The newest card is the last thing the model reads before it replies, so leaving the reminder out can make the agent switch the gender it uses for itself.

:::note
Tool scheduling (`WHEN_IDLE`, `SILENT`) only works for tools declared with `behavior=NON_BLOCKING`, on a model that supports asynchronous tools, such as Gemini 2.5 Flash Native Audio. Otherwise the scheduling value is ignored. Gemini 3.1 Flash Live waits for each tool response before it speaks again and doesn't support scheduling, so send session updates with `clientContent` right after `turnComplete` instead.
:::

### Replacing the instructions and tool list per card with `context_update`

On Vertex AI `gemini-3.8-live`, the WebSocket also accepts a `context_update` client message that replaces `systemInstruction` and the active `tools` list in place without reconnecting.

When a tool call moves the conversation to a new step card, you can send `context_update` inside that blocking tool handler right before returning the `FunctionResponse`:

1. Set `systemInstruction` to your base rules (with the opening greeting line replaced by an in-call reminder), the current step card, and the live session state. Because sliding-window compression keeps `systemInstruction` when it trims old history turns, the active card and session state never get dropped mid-call.
2. Set `tools` to only the tool schemas that the current step card needs (or `{}` on a talk-only closing card). You stop paying tool schema tokens on every turn for tools from earlier or later steps.
3. Return a one-line pointer in the `FunctionResponse` instead of repeating the full step card in the conversation history.

This is also the cheaper way to change instructions. An instruction update replaces the old one, so every turn pays for one step card. A step card sent as a user message stays in the conversation and is paid for again on every later turn. In our test on Vertex AI, after three card changes each turn cost 783 input tokens with instruction updates and 2,493 with user messages. If you only need to change the instructions (not the tools), the documented `send_client_content(turns=Content(role="system", ...), turn_complete=False)` call replaces them the same way, on both `gemini-3.8-live` and `gemini-live-2.5-flash-native-audio`.

`context_update` is exposed on the Vertex AI Live WebSocket today, though it is not yet in Google's public documentation or the `google-genai` SDK.
