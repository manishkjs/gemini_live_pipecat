Long-running duplex voice sessions face an invisible financial and performance trap: **quadratic token growth**.

Unlike standard chat interfaces where input is sent once, Gemini Live re-evaluates the entire context on every interaction:
1. **Quadratic Prompt Re-Billing**: The initial `systemInstruction` plus the entire carried turn history is re-billed on **every single model turn** as prompt text.
2. **Accumulating Audio Input Cache**: User audio streams in at **~25 tokens/second** (~1,500 tokens/minute). In Gemini Live, user speech accumulates in the context window as raw audio tokens and is re-billed at **\$3.00/1M tokens** (6x more expensive than text input at \$0.50/1M) on every subsequent turn.

Without deliberate optimization, an audio session balloons to tens of thousands of tokens within minutes, driving up latency and exploding inference costs.

---

## The Three Optimization Pillars

<Tabs>
  <TabItem label="1. Context Window Compression">

    ### Server-Side Compaction: The Safety Net

    Gemini Live provides built-in sliding-window context compression configured in `BidiGenerateContentSetup`. It is **not** an LLM summarizer; it is a deterministic **FIFO sliding window** that evicts the oldest conversation turns when context crosses a token threshold.

    | Field | What it does | Default | Production Target |
    | --- | --- | --- | --- |
    | `trigger_tokens` | Compaction fires when context crosses this count | ~80% of window (~32k) | **`5000`** (aggressive voice prune) |
    | `sliding_window.target_tokens` | How far context shrinks when compaction triggers | `trigger_tokens / 2` | **`3500` – `4000`** |

    System instructions and pinned prefix turns are always preserved; older turns are **FIFO-evicted**.

    ---

    ### Why Context Optimization Matters More with Large System Instructions

    If your agent uses a massive system prompt (2,000–5,000+ tokens of enterprise SOPs, product catalogs, schema specifications, and compliance rules), context optimization is **exponentially more critical**.

    Because Gemini Live does not discount carried system prompts across turns, that 4,000-token instruction is billed on Turn 1, Turn 2, Turn 10, and Turn 30. Over a 10-turn call, a 4,000-token prompt alone consumes **40,000 prompt tokens** before counting a single second of user audio:

    ```text
    Prompt Token Tax = Number of Turns × System Instruction Tokens
    ```

    When initial instructions are heavy, letting history accumulate unchecked accelerates quadratic cost explosion. Keeping context trimmed is the only way to prevent baseline prompt overhead from dominating call unit economics.

    ---

    ### 5k Compression: The "Blessing in Disguise"

    Most developers configure high triggers (`32,000` tokens), fearing that compacting at `5,000` tokens will drop conversation history prematurely.

    In duplex voice, **setting `trigger_tokens: 5000` is a massive blessing in disguise**:

    1. **Slashes the Expensive Audio Input Cache**:
       User audio costs **\$3.00 per million tokens**. While the assistant's generated audio is collapsed to text when returned to context, the **caller's spoken PCM audio remains in the context window as raw audio tokens**.
    2. **Halts Quadratic Audio Re-billing**:
       Without fast compaction, 2 minutes of user speech (~3,000 audio tokens) is re-billed at \$3.00/M on *every subsequent turn*. Over a 15-turn session, that audio cache is billed over and over again.
    3. **The Blessing**:
       Firing compaction at **5,000 tokens** aggressively flushes older raw audio turns from the prompt cache. The model retains the pinned system instruction and the last few immediate dialog turns, cutting prompt token volume by **60% to 75%** and keeping Time-to-First-Audio-Byte (TTFB) fast.

    ```python
    # Production Vertex AI / AI Studio Live Session Configuration
    context_window_compression = {
        "enabled": True,
        "trigger_tokens": 5000,   # "Blessing in disguise": flushes raw user audio cache early
        "sliding_window": {
            "target_tokens": 3500 # Drops ~1.5k tokens of stale audio, retaining recent turns
        }
    }
    ```

    <Aside type="tip" title="Tuning rule of thumb">
      Never leave `target_tokens` unset. The default drops 50% of the entire window (`trigger_tokens / 2`). Explicitly set `target_tokens` to `trigger_tokens - 1500` so it trims only the oldest audio turns while leaving conversational context intact.
    </Aside>

  </TabItem>

  <TabItem label="2. JIT Prompt Cards">

    ### Just-in-Time (JIT) Prompt Cards: The Funnel Optimization

    Rather than packing every conceivable instruction into a monolithic system prompt, **Just-in-Time (JIT) Prompt Cards** segment your agent's behavior into modular phase cards (`SOP_01_OPENING`, `SOP_02_DISCOVERY`, `SOP_03_PINCODE`, `SOP_04_BOOKED`).

    <PromptCardFunnel />

    ---

    ### The 0–5 Second Drop: Short-Call Economics

    In real-world enterprise telephony (tele-sales, outbound screening, IVR bots, lead qualification):

    > **30% to 50% of all phone calls drop within the first 0 to 5 seconds** (voicemail, immediate hangup, wrong number, prompt rejection).

    #### The Monolithic Failure
    If you deploy a monolithic 4,500-token prompt:
    - Even if the caller hangs up after **3 seconds**, you are billed for the full 4,500 prompt tokens.
    - If you run 100,000 calls and 40,000 bounce in under 5s, you burn **180,000,000 tokens** on dropped calls that never made it past "Hello".

    #### The Prompt Card Advantage
    With JIT Prompt Cards:
    - **Card 1 (`SOP_01_OPENING`)** is ultra-lean: ~100–150 tokens containing only voice persona, opening greeting, and hook. No objection matrix, no qualification logic, no booking schema.
    - **When calls are cut in the first 5 seconds, you save >95% on tokens** because the initial card has virtually no instructions.
    - Downstream phase cards are injected **only when the caller actually advances** into discovery or qualification.

    ---

    ### Dynamic Server-Side Card Injection

    Never rely on the model calling a tool to change phases—models frequently skip tool calls when users speak conversationally.

    Instead, track phases on the server from the live user transcription stream and inject prompt cards dynamically via `send_client_content(turn_complete=False)`:

    ```python
    # server/persona_prompt_cards/pragya_cards.py
    CARDS = {
        "SOP_01_OPENING": """
        You are Pragya, a luxury automotive concierge.
        Greeting: "Hello! Welcome to Silver Star Concierge. Are you inquiring about the GT Roadster or our bespoke bespoke leasing?"
        Tone: Refined, crisp, polite. Max 1 sentence.
        """, # ~120 tokens

        "SOP_02_DISCOVERY": """
        Phase 2: Qualify Interest & Model Preference.
        Ask whether they prefer weekend touring or track performance.
        Answer model questions concisely.
        """, # ~280 tokens

        "SOP_03_PINCODE": """
        Phase 3: Delivery Location.
        Request caller 6-digit postal code for showroom allocation.
        Format: Listen for 6 digits. Do not accept partial postal codes.
        """, # ~310 tokens

        "SOP_04_BOOKED": """
        Phase 4: Final Booking Confirmation.
        Confirm showroom test drive schedule and state booking reference ID.
        """  # ~210 tokens
    }
    ```

    ```python
    # Injected into the active live session by the server
    async def advance_phase_card(session, new_phase_id: str):
        card_content = CARDS.get(new_phase_id)
        if not card_content:
            return

        # send_client_content with turn_complete=False updates instructions without triggering output
        await session.send_client_content(
            turns=[{
                "role": "user",
                "parts": [{"text": f"[SYSTEM INSTRUCTION UPDATE - {new_phase_id}]:\n{card_content}"}]
            }],
            turn_complete=False
        )
    ```

    <Aside type="caution" title="Funnel Telemetry Rule">
      Derive phase progression on the server using deterministic regex or transcript keywords (e.g. 6-digit PIN code detected $\to$ advance to `SOP_03`). Never force the LLM to call `get_phase_card()`, which adds turn latency and token schema overhead.
    </Aside>

  </TabItem>

  <TabItem label="3. Client-Side Lossless Pruning">

    ### Lossless Client-Side Compaction

    The sliding window is a safety net, but client-side orchestration lets you reduce token consumption without discarding conversation context.

    | Lever | Mechanism | Benefit |
    | --- | --- | --- |
    | **Transcribe, then Prune Audio** | Evict raw client PCM audio turns older than 4–6 turns; retain their text transcripts in history. | Spoken audio is billed at \$3.00/M tokens. Text transcripts cost \$0.50/M tokens. You get the exact same semantic grounding at **83% lower cost**. |
    | **Rolling Structured FactStore** | Maintain a JSON digest (`<60 tokens`) of extracted user facts (`{name, pin, car_model, budget}`); re-inject each turn. | Survives sliding window eviction. Even if turn 1 was evicted 10 minutes ago, the bot remembers the user's postal code and preferred vehicle. |
    | **Pin System Instructions** | Declare persistent constraints in `setup.systemInstruction`. | The built-in sliding window never evicts system instructions or pinned prefix turns. |

    ---

    ### The FactStore Pattern

    ```python
    # Rolling fact store injected into turn context
    fact_digest = {
        "user_name": "Vikram",
        "pin_code": "110001",
        "vehicle_tier": "AMG GT Coupe",
        "budget": "Flexible"
    }

    # Re-inject during user turn payload
    turn_prefix = f"[Active Context FactStore: {json.dumps(fact_digest)}]\n"
    ```

## Architectural Comparison Matrix

| Strategy | Primary Optimization Target | When It Saves Money | Typical Token Savings | Latency Impact |
| --- | --- | --- | --- | --- |
| **JIT Prompt Cards** | Static prompt text overhead | In the first **0–5 seconds** (call drop / bounce funnel) and across staged multi-step workflows | **90%–96%** on bounced calls; **40%–60%** across long calls | Zero latency impact (cards injected asynchronously) |
| **5k Context Compression** | Stale user PCM audio cache | In active conversations running longer than **2–3 minutes** | **60%–75%** on cumulative audio cache re-billing | Neutral; reduces prompt processing latency |
| **Transcript-Only Pruning** | Historical audio input tokens | After turn 4 of any session | **~83%** on historical user turn volume | Positive (smaller token context = faster TTFB) |
| **Rolling FactStore** | Context survival across long calls | After sliding window eviction triggers | Lossless context retention in `&lt;60 tokens` | Negligible (`&lt;10ms` prompt overhead) |

<Aside type="tip" title="The Complete Production Mental Model">
  1. Start with a **featherlight Opening Prompt Card** so 0–5s dropped calls cost virtually nothing.
  2. Set **`trigger_tokens: 5000`** as a blessing in disguise to flush the expensive \$3.00/M user audio cache before it compounds.
  3. Let the server inject **JIT Phase Cards** as the caller advances through the conversation funnel.
  4. Use a **rolling FactStore** so critical user data survives FIFO eviction without carrying thousands of tokens.
</Aside>
