When [Pillar 1 (`SlidingWindow`)](/gemini_live_pipecat/optimization/sliding-window/) drops old audio turns at the 5,000-token boundary, any facts spoken in Turn 1 (such as the caller's name, postal code, or stated symptom) fall out of the raw audio window. Carried audio plus auto-transcripts (`~1,840 tokens/minute`, or `235 audio + 72 text = 307 tokens` per 10-second exchange) accumulate quickly, and audio tokens (`$3.00/1M`) cost 4x to 6x more per token and take ~3.3x more tokens than the equivalent text (`$0.50/1M` on 2.5 Native Audio, `$0.75/1M` on 3.1 Flash Live and 3.8 Live).

By extracting key facts into a lightweight backend `FactStore` (under 60 text tokens) and folding that summary into your `systemInstruction` on each step transition (see [Pillar 2](/gemini_live_pipecat/optimization/prompt-cards/)), you let the 5,000-token sliding window evict stale audio while retaining every detail the caller shared.

## Code pattern: Maintaining a `<60-token` `FactStore`

```python
import json
from google.genai import types


class CallFactStore:
    def __init__(self):
        self.facts = {
            "caller_name": None,
            "postal_code": None,
            "verified": False,
            "issue": None,
        }

    def render_summary(self) -> str:
        # Compact JSON stays under 60 tokens at $0.50-$0.75/1M text input
        return f"Session state: {json.dumps(self.facts, ensure_ascii=False)}"


# Include fact_store.render_summary() when refreshing systemInstruction so
# it overwrites in place and never gets evicted by the 5,000-token SlidingWindow:
async def sync_facts_into_system_instruction(
    session,
    base_rules: str,
    active_card: str,
    fact_store: CallFactStore,
):
    await session.send_client_content(
        turns=types.Content(
            role="system",
            parts=[
                types.Part(
                    text=f"{base_rules}\n\n{active_card}\n{fact_store.render_summary()}"
                )
            ],
        ),
        turn_complete=False,
    )
```
