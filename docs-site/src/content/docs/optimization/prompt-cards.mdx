## 1. Why dynamic prompt cards matter

In a multi-turn call, your system prompt and tool schemas are re-read on every turn. If you load a monolithic 4,500-token system prompt covering Greeting, KYC Verification, Troubleshooting, Billing, Upsell, and Cancellation at Turn 1, you pay to re-read all 4,500 tokens on every turn, even when the caller hangs up in the first 5 seconds.

Start the session with a compact 120-token opening card (keeping active prompt tokens averaging ~500 tokens across steps) and load the next phase card only when the conversation enters that stage.

## 2. How Gemini Live stores instructions vs. history (Replace vs. Stack)

A Gemini Live session has two memory regions that are sent to the model and billed on every turn:

- Region 1 (Top System Slot: `systemInstruction` and `tools`): Overwritten in place whenever you send a `role="system"` turn or `context_update`. When [Pillar 1 (`SlidingWindow`)](/gemini_live_pipecat/optimization/sliding-window/) trims old history at 5,000 tokens, Region 1 is never evicted.
- Region 2 (Conversation History: caller/agent audio, tool results, and `role="user"` turns): Append-only. Every card you drop into Region 2 stays there and is billed again on every later turn until the 5,000-token window trims it, at which point the card disappears and the model falls back to Turn 1's opening greeting (6 of 7 measured runs).

### Code pattern A: Replace instructions only (`role="system"`, documented on all Vertex AI Live models)

When your tool list stays the same and you only need to change the step instructions, use the documented `send_client_content` method with `role="system"` and `turn_complete=False`:

```python
from google.genai import types

BASE_RULES = (
    "You are Maya, a calm support specialist at Cymbal Fiber. "
    "Keep every reply to 1 or 2 short sentences, then pause for the caller."
)

STEP_CARDS = {
    "verify": "Current step: Verify identity. Ask for date of birth and postal code.",
    "troubleshoot": "Current step: Troubleshoot line. Check router lights one step at a time.",
    "wrap_up": "Current step: Wrap up. Read back the ticket number and wish the caller well.",
}


async def update_step_instruction(session, step: str, session_state: dict):
    # Always combine base rules + current card + live state so nothing is lost on overwrite
    full_instruction = (
        f"{BASE_RULES}\n\n"
        f"{STEP_CARDS[step]}\n"
        f"Session state: {session_state}"
    )
    await session.send_client_content(
        turns=types.Content(
            role="system",
            parts=[types.Part(text=full_instruction)],
        ),
        turn_complete=False,
    )
```

## 3. When to send an update (Mid-Speech vs. Inside a Tool Handler)

When you send an update matters just as much as how you format it:

- `clientContent` with `turn_complete=True` means *"the caller just finished speaking, reply now."* Sending it while the model is talking cuts the model off mid-sentence.
- `clientContent` with `turn_complete=False` (or `context_update`) is held in a server buffer and applied right before the next model turn (`14 of 16` mid-speech runs finished their sentence cleanly). However, it cannot steer a reply that is already in flight.
- Best timing: send the update inside a blocking tool handler right before returning the `FunctionResponse` (or right after receiving `turnComplete`). Because the model is paused waiting for your tool result, the update never races active speech (`5 of 5` runs).

### Example: Breaking down an 8-step flight-booking voice agent

To see why swapping tools per card saves so many tokens, consider a real flight-booking voice agent (**"Cymbal Travel"**) that guides a caller from greeting to payment. Across the whole call, the agent uses 6 tools (measured on Vertex AI `gemini-3.8-live` as the `usage_metadata.prompt_token_count` delta above a zero-tool session):

1. `set_call_language` (`93` billed tokens): records the caller's preferred spoken language for the session.
2. `resolve_airport_code` (`44` billed tokens): resolves a city or region name to an IATA airport code.
3. `find_available_flights` (`511` billed tokens): queries outbound and return flights by date, time window, or fare tier.
4. `update_selected_itinerary` (`164` billed tokens): locks in a chosen flight leg, updates cabin filters, or reopens route search.
5. `save_passenger_manifest` (`457` billed tokens): validates passenger counts, legal names, mobile number, and email address.
6. `dispatch_checkout_link` (`57` billed tokens): sends the checkout link once the itinerary and passenger manifest are confirmed.

If you declare all 6 tools in `setup.tools`, Gemini 3.8 Live bills all **1,326 tool-schema tokens on every single turn** of the call (`93 + 44 + 511 + 164 + 457 + 57 = 1,326` in `usage_metadata.prompt_token_count`, or `~2,198` tokens if counted as raw serialized JSON text), even on Turn 1 when the agent is only asking which language the caller prefers, and on the final turn when passenger details are already done.

With `context_update`, each of the 8 prompt cards registers only the tools needed for that step:

| Prompt card in the flight-booking call | What happens in this step | Tools registered for this card | Tool tokens billed per turn (`gemini-3.8-live`) |
| :--- | :--- | :--- | :--- |
| Card 1 | Greeting &amp; language choice | `set_call_language` | `93 tokens` (vs. 1,326 for all 6) |
| Card 2 | Route &amp; travel date intake | `set_call_language`, `find_available_flights`, `resolve_airport_code` | `648 tokens` (`93 + 511 + 44`) |
| Card 3 | Flight selection &amp; filter refinement | `set_call_language`, `update_selected_itinerary`, `find_available_flights` | `768 tokens` (`93 + 164 + 511`) |
| Cards 4–7 | Passenger count, names, phone &amp; email | `set_call_language`, `save_passenger_manifest`, `update_selected_itinerary` (`find_available_flights` &amp; `resolve_airport_code` dropped) | `714 tokens` (down from 1,225 with `find_available_flights`) |
| Card 8 | Checkout link &amp; confirmation | `set_call_language`, `dispatch_checkout_link` (`save_passenger_manifest` &amp; `update_selected_itinerary` dropped) | `150 tokens` (down from 771 on Cards 4–7 + checkout) |
| Optional farewell (after Card 8) | Talk-only closing | `tools: {}` (empty wrapper clears all tools) | `0 tool tokens` |

### Python pattern: `send_context_update` and tool handler

You do not need a wrapper class to use `context_update`. Inside your blocking tool handler, send the `context_update` JSON frame on `session._ws` right before returning the `FunctionResponse`:

```python
import json
from google.genai import types


async def send_context_update(
    session,
    system_instruction: str,
    tool_declarations: list[dict],
) -> None:
    """Replace systemInstruction and active tools in place on Vertex AI gemini-3.8-live.

    Pass tool_declarations=[] to clear all tools (sends {"tools": {}}).
    """
    frame = {
        "context_update": {
            "systemInstruction": {"parts": [{"text": system_instruction}]},
            "tools": (
                {"tools": [{"functionDeclarations": tool_declarations}]}
                if tool_declarations
                else {}
            ),
        }
    }
    await session._ws.send(json.dumps(frame))


async def on_tool_call(session, function_call, active_tool_names: set[str], run_step):
    # function_call is one item from server_message.tool_call.function_calls
    # 1. Guard against the model imitating an old tool call from earlier history turns
    if function_call.name not in active_tool_names:
        await session.send_tool_response(
            function_responses=[
                types.FunctionResponse(
                    id=function_call.id,
                    name=function_call.name,
                    response={"error": f"{function_call.name} is not active in this step."},
                )
            ]
        )
        return

    # 2. Run your business logic -> get next card text, session state, and next card's tools
    next_instruction, next_tool_decls, next_tool_names = run_step(
        function_call.name, function_call.args or {}
    )
    active_tool_names.clear()
    active_tool_names.update(next_tool_names)

    # 3. Swap systemInstruction + tools while the model is paused waiting on this tool result
    await send_context_update(session, next_instruction, next_tool_decls)

    # 4. Return a 1-line pointer instead of repeating the 600-token card in history
    await session.send_tool_response(
        function_responses=[
            types.FunctionResponse(
                id=function_call.id,
                name=function_call.name,
                response={"status": "ok", "guidance": "Follow the current step in your system instruction."},
            )
        ]
    )
```

:::caution[`context_update` is exposed on the wire, but not yet in public documentation or the SDK]
- No released version of `google-genai` has a typed helper for `context_update`, and no public Google documentation page describes it yet. You write raw JSON to `session._ws.send(...)`.
- It works on Vertex AI `gemini-3.8-live` (`v1beta1` and `v1`). Google AI Studio ignores it, and `gemini-live-2.5-flash-native-audio` rejects it and closes with `1007` (use `role="system"` client content on 2.5 instead).
- Every `context_update` replaces (does not merge) the declared tools. Keep global tools like `set_call_language` in every card's list, and send `"tools": {}` when you want to clear all tools.
:::
