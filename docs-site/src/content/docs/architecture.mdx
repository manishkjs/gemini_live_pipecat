Gemini Live is **stateful and bidirectional**. Four concepts govern every production voice session: two input channels, the turn lifecycle, interruptions, and session resumption.

## Continuous conversation over a single socket

<DuplexFlow />

Audio moves in both directions continuously over one persistent WebSocket. There is no request/response polling loop, and the model can begin speaking as soon as server-side Voice Activity Detection (VAD) detects the end of a user turn.

## Two input channels

| Channel | Purpose | Enters history? | Interrupts model? |
| --- | --- | --- | --- |
| **`realtimeInput`** | Continuous microphone or camera stream | Yes (user speech turns) | Triggers server VAD |
| **`clientContent`** | Explicit turn-based messages or context injection | Yes | **Yes with `turnComplete: true`**; usually not with `turnComplete: false` |

Send live microphone audio on `realtimeInput`. Use `clientContent` only for explicit text turns or silent server-side context updates (`turnComplete: false`).

<Aside type="caution" title="Do not send mic audio on clientContent">
A `clientContent` message with `turnComplete: true` is a new user turn and interrupts any active model generation, so streaming microphone chunks over `clientContent` cuts the model off on every packet. A `turnComplete: false` update sent mid-reply did not cut off speech in 14 of 16 measured runs on Vertex AI `gemini-3.8-live` and `gemini-live-2.5-flash-native-audio`; it applies from the next turn.
</Aside>

## The turn lifecycle

Three server signals govern turn state and audio playback:

| Signal | What it means | How your client should react |
| --- | --- | --- |
| **`generationComplete`** | The model finished generating tokens on the server. | Stop showing a "thinking/generating" indicator, **but keep the speaker state active** until your local audio playout queue drains. |
| **`turnComplete`** | The logical turn has concluded on the wire. | Flush your per-turn transcript buffer, record `usageMetadata` once, and mark the turn complete in logs. |
| **`interrupted`** | Server VAD detected user barge-in during model output. | Immediately discard all unplayed audio chunks in your local playback queue. |

The gap between `generationComplete` and local buffer drain is often 1 to 3 seconds. If you transition UI state or fire post-speech actions on `generationComplete` instead of waiting for the audio queue to finish playing, your UI will claim the agent is silent while it is still speaking.

## Interruptions (barge-in)

<BargeIn />

When a caller speaks over the agent, the server sends `interrupted` and halts downstream generation. However, your client has already received several seconds of generated audio ahead of real-time playback. If you do not flush that local buffer, the agent continues talking over the caller.

Flush the playback queue immediately on `interrupted`:

```javascript
function onInterrupted() {
  playbackQueue.length = 0;   // discard buffered PCM chunks
  currentSource?.stop();      // stop active Web Audio node immediately
}
```

## Session resumption

<SessionLifecycle />

The server rotates WebSocket connections roughly every **10 to 15 minutes**. Shortly before closing, it emits a `sessionResumptionUpdate` frame containing a `newHandle` and `lastConsumedClientMessageIndex`, then closes the socket with code `1008`. Treat a `1008` close following a resumption update as routine rotation, never as a fatal crash.

To resume without losing conversation context:

1. Enable `sessionResumption: {}` in your initial `setup` frame.
2. Assign a monotonically increasing index to each outbound client message and hold unconfirmed messages in a ring buffer.
3. Whenever `sessionResumptionUpdate` arrives, store `newHandle` and drop buffered messages up to `lastConsumedClientMessageIndex`.
4. When the socket closes, open a new WebSocket passing `handle: newHandle` in `setup.sessionResumption`, wait for `setupComplete`, and replay any remaining unconfirmed messages before sending new turns.
5. If a handle has expired (over 2 hours old), open a fresh session and re-hydrate state from your application's FactStore.

<Aside type="tip">
Frameworks like Pipecat manage session resumption and message replay automatically (see [Choosing a framework](/gemini_live_pipecat/frameworks/)). When building directly on a raw WebSocket, implement this replay buffer in your session state machine.
</Aside>
