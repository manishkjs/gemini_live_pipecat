Gemini Live is **stateful and bidirectional**. Four concepts explain almost
everything you will see in production: two input channels, the turn
lifecycle, interruptions, and session resumption.

## Continuous conversation over a single socket

<DuplexFlow />

There is no "send request, await response" loop. Audio moves in both directions
continuously over a single WebSocket, and the model can start speaking before you
stop.

## Two input channels

| Channel | Purpose | Enters history? | Interrupts model? |
| --- | --- | --- | --- |
| **`realtimeInput`** | Continuous microphone/camera stream | No | No |
| **`clientContent`** | Explicit turn-based messages | Yes | Yes |

Send live microphone audio as `realtimeInput`. Use `clientContent` only for
explicit turns you want committed to conversational history.

<Aside type="caution">
Do not swap these channels. Microphone audio sent as `clientContent` interrupts
the model on every chunk and bloats context. A user turn sent as `realtimeInput`
is never saved to session history.
</Aside>

## The turn lifecycle

Three server signals govern playback:

| Signal | What it actually means |
| --- | --- |
| **`generationComplete`** | The model finished generating tokens. Your playback buffer may still hold seconds of audio. |
| **`turnComplete`** | The logical end of the turn. |
| **`interrupted`** | The user barged in. Discard queued audio immediately. |

The gap between `generationComplete` and `turnComplete` is where most "the agent talks over me" bugs occur.

## Interruptions (barge-in)

<BargeIn />

Conversational voice requires callers to talk over the agent. When the server detects
speech during playback, it sends `interrupted`. The audio you must discard
is audio **you have already received**. If you only stop requesting new chunks,
the agent keeps talking from the local playout buffer.

Handle it with an immediate stop:

```javascript
function onInterrupted() {
  playbackQueue.length = 0;   // drop unplayed chunks
  currentSource?.stop();      // cut off active playback immediately
}
```

## Session resumption

<SessionLifecycle />

The server closes sessions proactively roughly every 10 to 15 minutes. This is
expected protocol behavior. It emits a `sessionResumptionUpdate` containing a handle,
then closes with code `1008`. Treat this close as routine rotation rather than a crash.

To resume cleanly:

1. Enable resumption in `setup`.
2. Number and buffer every message you send.
3. The server reports the last index it safely received. Discard buffered messages up to that index.
4. On reconnect, open a new socket with the stored handle, then replay the remaining buffer before sending new turns.
5. If the handle expired, start a fresh session.

<MessageReplay />

<Aside type="tip">
Higher-level frameworks like Pipecat handle resumption state machines automatically. See
[Choosing a framework](/gemini_live_pipecat/frameworks/). On a raw WebSocket, you implement
this message replay queue directly.
</Aside>

## Jitter buffering

Networks deliver audio packets unevenly. A small playout buffer (queuing a few chunks and playing them at a steady cadence) trades minimal latency for smooth, glitch-free audio. See
[Audio engineering](/gemini_live_pipecat/audio-engineering/) for buffer tuning.
